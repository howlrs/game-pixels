# 99. 未決事項とレビュー履歴

本書執筆時点で結論に至っていない論点と、Gemini レビューの採否一覧をここに集約する。

## 19.1 未決事項

### 19.1.1 内部解像度のデフォルト

- 候補 A: 256×240 (NES 互換、4:3)
- 候補 B: 480×270 (16:9 拡張)
- 現状: B 採用。ただし「クラシック準拠 を強く打ち出す路線」では A を採用する判断もあり得る。デザイン方針が決まったら再検討。

### 19.1.2 World Map の有無

- 候補 A: SMB1 風 「クリアで自動で次へ」
- 候補 B: SMB3 風 ステージ選択マップ
- 現状: B (再挑戦・ショートカットの自由度が高いため)。Web の "ステージ単発挑戦" UX とも親和的。

### 19.1.3 リスポーン時のサイズ

- 候補 A: Small に強制 (古典互換)
- 候補 B: 死亡前のサイズで復帰 (モダン)
- 現状: A。ただし a11y "ジャンプアシスト" 等を有効にしている場合は B も提供可。

### 19.1.4 ステージ進行の自動セーブ

- 各ステージのチェックポイントを永続化するか?
- 現状: 永続化しない (古典互換)。a11y モードでは別途検討。

### 19.1.5 マルチプレイ拡張

- ローカル協力 (画面分割なし、画面共有) は技術的に検討余地あり。
- ネットワーク同期は本書範囲外。決定論を活かしたロックステップ方式が候補。

### 19.1.6 Mario Maker 風 UGC

- ステージエディタの提供。コミュニティ機能の有無。
- 範囲外。アーキテクチャ (§94) はデータ駆動なので拡張余地あり。

### 19.1.7 数値定数の最終調整

- 本書では SMB1 由来の数値を起点としているが、Web の入力レイテンシ (タッチ等) を考慮し、**全プレイテストののち調整**。
- 調整は `core/physics-constants.ts` で集中管理 (§94)。

### 19.1.8 ECS への移行

- MVP は OOP。アクター数や拡張性で限界が見えたタイミングで `bitECS` 等への移行を検討。
- 移行コストとリスクは別途見積もり。

### 19.1.9 マネタイズ

- 範囲外。広告/IAP/購入のいずれも MVP に含めない。
- 設計上はクラウド同期の存在を前提に「アカウント識別」を抽象化しておく。

## 19.3 設計レビューの観点 (チェックリスト)

実装着手前に以下を再確認する:

- [ ] 物理定数 (§20) は単位・上限・下限が明示されているか
- [ ] 衝突 (§30) は軸分離・サブステップ・ゴーストバーテックス対策が記述されているか
- [ ] プレイヤー (§40) のサイズ階層と状態機械が一致しているか
- [ ] 敵 (§50) の踏みつけ可否、甲羅、連鎖スコアが網羅されているか
- [ ] アイテム (§60) の抽選とブロック種別が網羅されているか
- [ ] カメラ (§70) は両方向 + 縦持ちで破綻しない設計か
- [ ] ワールド (§80) のデータ形式は拡張可能か (Pipe Warp, Trigger)
- [ ] 入力 (§90) は 3 系統 + リマップ + ゲームパッドのリビルドが具体か
- [ ] 描画 (§91) は Canvas2D / WebGL / WebGPU の縮退が安全か
- [ ] オーディオ (§92) の自動再生制限と SE プールの扱いが明確か
- [ ] セーブ (§93) はマイグレーションとフォールバックを持つか
- [ ] アーキテクチャ (§94) の依存方向は決定論を保つか
- [ ] パフォーマンス (§95) のフレームバジェットがモバイルで実現可能か
- [ ] アクセシビリティ (§96) は OFF/ON が同等の動作か
- [ ] クロスデバイス (§97) はセーフエリアと方向回転を扱うか
- [ ] ピクセル現代化 (§98) は物理と視覚を独立に扱うか
